# Consistency-Gated RAG

A **Retrieval-Augmented Generation** system that only triggers document retrieval when the LLM is uncertain about its answer. Rather than always paying the latency and cost of a RAG pipeline, the system uses **self-consistency** as a proxy for model confidence to decide whether retrieval is actually needed.

---

## Motivation

Standard RAG systems retrieve documents on every query regardless of whether the model already knows the answer. This introduces unnecessary latency and API cost for questions the model can answer confidently from its parametric knowledge (e.g. *"What is the capital of France?"*).

This project implements a **consistency gate**: the model answers the same question multiple times, and the semantic agreement between those answers is used as a confidence signal. Only when the model is uncertain (i.e. answers diverge) does the system fall back to grounded retrieval.

This approach falls under the broader paradigm of **adaptive RAG**, where the system autonomously decides whether to call a retrieval agent and which collection to query, rather than systematically retrieving on every input.

This is grounded in two complementary ideas from the NLP literature:

- **Self-Consistency** (Wang et al., 2022): sampling multiple answers from an LLM and taking the majority is more reliable than greedy decoding. Agreement across samples correlates with answer correctness.
- **Selective RAG / Active RAG**: triggering retrieval only when necessary, rather than unconditionally, improves efficiency without sacrificing accuracy.

## Architecture

```
User Query
    │
    ▼
┌─────────────────────────────────┐
│           ROUTER (main.py)      │
│                                 │
│  1. Query LLM × 3  (temp=0.7)   │
│  2. Embed answers               │
│  3. Pairwise cosine similarity  │
│  4. Avg score ──► threshold ?   │
└─────────────────────────────────┘
         │                  │
    score ≥ 0.9         score < 0.9
  (high confidence)   (low confidence)
         │                  │
         ▼                  ▼
   Direct Answer      ┌───────────────────────┐
                      │    RAG PIPELINE        │
                      │      (rag.py)          │
                      │                        │
                      │  1. Encode query       │
                      │  2. FAISS IVF search   │
                      │  3. Build context      │
                      │  4. Grounded LLM call  │
                      └───────────────────────┘
                               │
                               ▼
                       Grounded Answer
                       (with citations)
```

The FAISS index is built **offline** by `src/indexer.py` and loaded at startup by `src/rag.py`.

## Technical Choices

### Embedding Model: `all-MiniLM-L6-v2`

A **bi-encoder** from the Sentence Transformers library. It uses **mean pooling** over all token embeddings (weighted by the attention mask) to produce a single 384-dimensional dense vector per input. This captures semantic meaning across the full input sequence, enabling similarity search that goes beyond keyword overlap. Note that the model has a **maximum sequence length of 256 word pieces** — any input beyond that is silently truncated.

The same model is used in two places:
1. **Indexing/retrieval** (in `src/rag.py` and `src/indexer.py`): to encode document chunks and queries into the same vector space.
2. **Consistency scoring** (in `src/main.py`): to embed the LLM's multiple answers and measure their pairwise semantic agreement.

Using a single shared model for both tasks is a deliberate simplification. A cross-encoder would be more accurate for re-ranking but is far too slow for retrieval over tens of thousands of chunks.

### FAISS with IVF and Inner Product + L2 Normalization

L2-normalized vectors with inner product search is mathematically equivalent to cosine similarity. Vectors are normalized at both indexing time and query time with `faiss.normalize_L2`.

The index uses `IndexIVFFlat` (Inverted File Index) with **256 Voronoi cells** for approximate nearest neighbor search. During indexing, k-means partitions all vectors into 256 clusters. At search time, only the `nprobe=16` closest clusters are scanned, giving a ~16x speedup over brute-force with minimal recall loss. This is appropriate at the current scale (~118k vectors). At larger scale (millions+), `IndexIVFPQ` (with Product Quantization for memory compression) or `IndexHNSWFlat` (graph-based ANN) would be better trade-offs.

### Chunking Strategy

Documents are split into **128-word chunks with a 20-word overlap** using a sliding window. The overlap ensures that context at chunk boundaries is not lost. Chunks shorter than 20 words are discarded as noise.

Word-level chunking (rather than character-level) is used because it maps more intuitively to semantic content density. The 128-word size is a practical sweet spot: long enough to carry sufficient context for embedding, short enough that the retrieved passage remains targeted.

### Knowledge Base: Google Natural Questions

The index is built from the [Natural Questions](https://ai.google.com/research/NaturalQuestions) dataset (307k examples in the train split), which contains real Google Search queries paired with full Wikipedia articles. Each example in the dataset is a `(question, document)` pair with rich annotations (long/short answer spans, yes/no labels), but this project only uses a subset of the available fields:

- **For indexing** (`src/indexer.py`): the full Wikipedia page HTML (`document.html`) is cleaned with BeautifulSoup and chunked into embeddings. The source URL (`document.url`) is stored as metadata alongside each chunk. Note that the same Wikipedia page can appear multiple times in the dataset (paired with different questions), so the index may contain duplicate chunks.
- **For evaluation** (`eval/run_eval_ir.py`): the question text (`question.text`) is used as a query, and the associated document URL (`document.url`) serves as ground truth — a retrieved chunk is considered relevant if its source URL matches.

The number of examples to index is controlled by the `NB_ROWS` constant in `src/indexer.py`. Note that each NQ example contains a **full Wikipedia page** (typically 3,000–5,000 words), which is chunked into many vectors: for instance, 2,000 documents yield ~118,000 chunks in the index (a ~59x expansion). The dataset's annotations (answer spans, candidate paragraphs) are not used: the project treats NQ as a **document retrieval** benchmark rather than an extractive QA benchmark.

### Consistency Gate Threshold

The threshold is set to **0.9**. A score of 1.0 means the three answers are semantically identical; a score near 0 means they are completely different. At 0.9, the gate tolerates minor phrasing variation while catching genuine uncertainty (diverging facts, hallucinations, hedging). This value was selected empirically and can be tuned via the `CONSISTENCY_THRESHOLD` constant in `src/main.py`.

### LLM: Mistral Small

`mistral-small-latest` is used for both the consistency sampling and the grounded generation step. It offers a good accuracy/cost trade-off. The temperature is set to **0.7** during consistency sampling to introduce controlled variability — a temperature of 0 would always return the same answer, making the consistency check meaningless.

## Evaluation

The IR component is evaluated in [`eval/evaluation_ir.ipynb`](eval/evaluation_ir.ipynb) and [`eval/run_eval_ir.py`](eval/run_eval_ir.py) on a random sample of **200 questions** from Natural Questions whose ground-truth document URL is present in the index.

| Metric     | Value   |
|------------|---------|
| MAP@20     | 0.761   |
| MRR        | 0.837   |
| Recall@1   | 0.795   |
| Recall@5   | 0.900   |
| Recall@20  | 0.940   |
| Questions  | 200     |
| K (top-k)  | 20      |
| Index size | 118,283 vectors (from 2,000 NQ documents) |

Ground truth is determined by URL matching: a retrieved chunk is considered relevant if its source URL matches the document URL associated with the question in the Natural Questions dataset.

The evaluation also produces an **11-point interpolated precision-recall curve** (`pr_curve.png`), a standard IR visualization that shows the trade-off between precision and recall across all queries.

### QA Evaluation (end-to-end)

The full pipeline is evaluated in [`eval/run_eval_qa.py`](eval/run_eval_qa.py) on 50 NQ questions that have gold short answers. For each question, the consistency gate runs first; uncertain questions are answered both directly (no retrieval) and via the RAG pipeline. Answers are compared to the gold short answer using **token F1** (bag-of-words overlap, the standard metric for free-text QA).

|                              | Avg Consistency Score | Avg Token F1 |
|------------------------------|----------------------|--------------|
| Confident (gate passes, 44%) | 0.987                | 0.597        |
| Uncertain — direct answer    | 0.608                | 0.166        |
| Uncertain — RAG answer       | 0.608                | **0.373**    |

Key takeaways:
- **The gate correlates with knowledge**: high-consistency questions (score ~0.99) have 3.6x higher F1 than low-consistency ones (0.60 vs 0.17), confirming that self-consistency is a valid confidence proxy.
- **RAG improves uncertain answers**: on questions where the LLM is uncertain, retrieval more than doubles the token F1 (+0.21), validating the core hypothesis.
- **44% of queries skip retrieval** with no quality loss, saving latency and API cost.

**Concrete example** — *"Who won series 7 of Great British Bake Off?"*

| | Value |
|---|---|
| Consistency score | **0.16** (very low — the 3 sampled answers all disagree) |
| Direct answer (no RAG) | "Yasmin" (hallucinated, F1 = 0.0) |
| RAG answer | **"Candice Brown"** (correct, F1 = 1.0) |
| Gold answer | Candice Brown |

The model has no reliable knowledge of this fact: its three samples diverge completely (score 0.16), producing a hallucinated name. The consistency gate catches this uncertainty and routes to the RAG pipeline, which retrieves the correct Wikipedia passage and generates the right answer.

## Installation

### Prerequisites

- Python 3.9+
- A [Mistral AI API key](https://console.mistral.ai/)

### Setup

1. **Clone the repository**
   ```bash
   git clone https://github.com/yourusername/Consistency-Gated-RAG.git
   cd Consistency-Gated-RAG
   ```

2. **Install dependencies**
   ```bash
   pip install mistralai sentence-transformers faiss-cpu datasets numpy python-dotenv beautifulsoup4 tqdm
   ```

3. **Configure your API key**

   Create a `.env` file at the project root:
   ```env
   MISTRAL_API_KEY=your_api_key_here
   ```

## Usage

### Step 1 — Build the knowledge base (offline, run once)

This streams the Natural Questions dataset, processes `NB_ROWS` documents (default: 2,000), and writes `my_rag_db.index` and `my_rag_db.json` to disk.

```bash
python src/indexer.py
```

> **Note:** Each NQ document is a full Wikipedia page that expands into many chunks (~59x). 2,000 documents produce ~118k vectors. Adjust `NB_ROWS` in `src/indexer.py` to control scale.

### Step 2 — Run the assistant

```bash
python src/main.py
```

The system will prompt for questions interactively. For each query it prints the consistency score and indicates whether the answer came directly from the model or from the RAG pipeline.

```
=== ASSISTANT INTELLIGENT (CONSISTENCY-GATED RAG) ===
Seuil de confiance : 0.9
Tape 'q' pour quitter

 Votre question : What is the speed of light?
[ROUTER] Score de confiance: 0.97
VALIDE : Le modele connait la reponse !

 Reponse:
The speed of light in a vacuum is approximately 299,792,458 metres per second...

 Votre question : Who won the 1987 Ecuadorian elections?
[ROUTER] Score de confiance: 0.61
>>> DOUTE (Score < 0.9): Activation du RAG.
Recherche dans la base de documents...

 Reponse verifiee (RAG) :
...
```

### Step 3 — (Optional) Evaluate the IR component

Run `python eval/run_eval_ir.py` or open [`eval/evaluation_ir.ipynb`](eval/evaluation_ir.ipynb) to compute MAP@20, MRR, and Recall@k on 200 questions from Natural Questions.

## Limitations & Future Work

- **No re-ranker**: retrieved chunks are ordered by cosine similarity with no cross-encoder re-ranking step. Adding a cross-encoder on the top-k results would improve precision.
- **Fixed threshold**: the 0.9 consistency threshold is hand-tuned. A learned or adaptive threshold (e.g. calibrated on a held-out set) would be more robust.
- **No answer fusion**: when RAG is triggered, the original direct answers are discarded. A future version could fuse the direct and grounded answers.
- **Knowledge base scope**: currently 2,000 NQ documents are indexed (~118k chunks). Scaling to more documents or a broader corpus would improve recall.
- **IVF approximate search**: `IndexIVFFlat` with `nprobe=16` may miss nearest neighbors near cluster boundaries. For larger corpora, switching to IVFPQ (for memory compression) or HNSW (for better recall) would be beneficial.
